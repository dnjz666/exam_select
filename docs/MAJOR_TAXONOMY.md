# 专业分类规则库（MAJOR_TAXONOMY.md）

> **本文件是"专业怎么归类"的唯一权威说明**，配套实现：
> * 规则数据（编辑源，JSON）：`data/taxonomy/major_taxonomy.json`
> * 规则数据（运行时，Python 模块）：`backend/app/core/major_taxonomy_data.py`
>   —— 由 `scripts/build_major_taxonomy_data.py` 生成，**勿手改**
> * 判定逻辑：`backend/app/core/major_taxonomy.py`（纯函数，ADR-003）
> * 单测：`backend/tests/test_major_taxonomy.py`
>
> 与 `docs/DOMAIN_RULES.md` §5.2（专业匹配打分表）配套阅读。

---

## 0. 为什么需要这份规则库（M6 实测缺陷，ADR-018）

浙江真实数据的 `majors.category` 与 `majors.discipline` **全部为 NULL**——
官方投档表只发布**专业名**，不发布专业目录归属。后果是三个下游全部失效：

| 受影响处 | 症状 |
|---|---|
| `scoring.major_match_score` | "同一专业类 0.80 / 同一门类 0.55 / 相关门类 0.30" **三档永不命中**，只剩"专业名完全一致"能拿分 → 推荐页勾"意向专业"形同虚设 |
| `probability` Step 0 类比池 | `analog_key(..., discipline=None)` 让**所有专业塌缩进同一个桶** → 拿"社会学"去类比"临床医学" |
| 前端"意向专业"筛选 | 无法按专业类/门类聚合 |

本规则库把**招生专业名**确定性地映射回教育部专业目录，使这三处重新工作。

## 1. 四级模型

| 级别 | 名称 | 取值来源 | 示例 |
|---|---|---|---|
| **L1** | 门类 | 教育部本科目录 **12 门类**；专科为 **19 大类** | `工学` |
| **L2** | 专业类 | 教育部本科目录 **93 专业类**；专科 97 专业类 | `计算机类` |
| **L3** | 专业 | 去括号后的**专业基名** | `计算机科学与技术` |
| **L4** | 招生方向 | 括号内后缀 | `(中外合作办学)` |

**为什么要 L4**：同一个 L3 专业在不同招生方向下，**录取位次可能相差数万名**。
例如 `软件工程(中外合作办学)` 与 `软件工程` 是两个独立投档单位。
把方向建成独立维度后，才能：
* 在推荐卡片上明示"中外合作办学"（AGENTS.md 名师铁律 10：**贵的不一定差，但必须让家长看见**）；
* 识别"拔尖基地班"这类通常**保研率更高**的方向；
* 让"专业名匹配"不被方向后缀打断（见 §5）。

## 2. 数据来源与核实状态

| 层级 | 来源 | URL | 核实年 |
|---|---|---|---|
| 本科 12 门类 / 93 专业类 / 专业名 | 教育部《普通高等学校本科专业目录（2024年）》 | [plan.hnist.cn](https://plan.hnist.cn/info/1013/1430.htm) | 2024 |
| 高职专科 19 大类 | 教育部《职业教育专业目录（2021年）》 | [moe.gov.cn](http://www.moe.gov.cn/srcsite/A07/moe_953/202103/t20210319_521135.html) | 2021 |

**诚实声明（与项目"宁可不答，不可编造"一致）**：

1. 本科 12 门类 / 93 专业类的**结构**为目录原文。
2. 专科 **19 大类**为目录原文；其下的**专业类清单为常见项整理**，可能不完整
   （规则数据中标为 `zhuanke_source_url` 并附 caveat）。专科专业名最终用
   **本科专业类词汇**归类（见 §3），因此该不完整性的影响被限制在"专科大类展示"上。
3. `discipline_keywords`（专业类关键词）与 `direction_*`（招生方向）是
   **项目内部约定**，不是教育部口径。每条判定都能通过 `classify_major()` 返回的
   `evidence` 字段追溯到**命中的具体关键词**，可逐条审计。
4. **无法归类的名称一律 `UNCLASSIFIED`**，不填任何"看起来合理"的值。

## 3. 关键设计决策

### 3.1 专科用同一套专业类词汇（★ 项目约定，非教育部口径）

库中 `duration=3` 的 1,634 个投档单位是**高职专科**专业。专科目录有自己的一套专业类名，
但本规则库**故意**把专科专业名也归入本科的 93 个专业类。

**理由**：唯一消费方是"专业类匹配打分"与"类比池"，两者都要求**单一可比的专业类空间**。
若本科/专科各用一套词汇，则 `计算机类`（本科）与 `计算机类`（专科）会被判成不同专业类，
匹配与类比都会断裂。

**代价**：`大数据技术`（专科）与 `数据科学与大数据技术`（本科）会被判为**同一专业类**，
两者在打分上不可区分。这是刻意的取舍，已在此声明。

### 3.2 招生方向不落库，运行时现算

`majors` 表**不新增** `admission_direction` 列。原因：方向 100% 可由专业名推出（纯函数），
落库等于同一事实存两份，必然漂移。方向与基名在 `classify_major()` 中现算。

`majors.category` / `majors.discipline` **则落库**——它们要参与 SQL 层筛选与缓存，
且是"已审计"的口径（见 §6 回填）。

### 3.3 规则数据是 Python 模块，不是 JSON 文件

`core/` 禁止文件 IO（ADR-003）。静态参考数据一律以模块常量内联，
与 `scoring.CITY_TIERS` / `scoring.RELATED_CATEGORY_MAP` 的做法一致。

因此采用**两步**：JSON（`data/taxonomy/major_taxonomy.json`）是**编辑源**（1,100+ 条映射用 JSON
更易读易审），由 `scripts/build_major_taxonomy_data.py` 生成 Python 模块并做不变量校验。
`core/` 内只有代码，不含数据文件。

## 4. 判定优先级（先命中先返回，绝不"猜"）

```
classify_major(name)
  │
  ├─ 0. 拆方向：base, direction = split_direction(name)
  │
  ├─ 1. base ∈ MAJOR_EXACT                     → CATALOG_EXACT      (门类+专业类)
  │
  ├─ 2. base 本身是专业类名（"计算机类"）        → DISCIPLINE_NAME    (门类+专业类)
  │
  ├─ 3. 大类招生（试验班/实验班/创新班/基地班）
  │      ├─ 3a. 方向能收窄到**专业类**          → DIRECTION_NARROWED (门类+专业类)
  │      ├─ 3b. 登记在 TRAINING_CLASS_RULES     → TRAINING_CLASS     (**仅门类**)
  │      ├─ 3c. 方向只能定到**门类**            → TRAINING_CLASS     (**仅门类**)
  │      └─ 3d. 都定不出来                      → TRAINING_CLASS     (无门类，诚实标注)
  │
  ├─ 4. 命中 DISCIPLINE_KEYWORDS（**最长关键词优先**）→ KEYWORD_RULE  (门类+专业类)
  │
  └─ 5. 都不命中                                → UNCLASSIFIED      (门类=None)
```

**为什么"最长关键词优先"**：否则 `机械` 会抢走 `机械电子工程` 的匹配，
把本该归 `机械类` 的专业错误处理。规则表在模块加载时按关键词长度降序排好。

**`TRAINING_CLASS` 与 `UNCLASSIFIED` 的区别**（易混淆，代码里用两个属性区分）：

| 状态 | `category` | `discipline` | `is_classified` | `has_discipline` |
|---|---|---|---|---|
| `CATALOG_EXACT` / `DISCIPLINE_NAME` / `KEYWORD_RULE` / `DIRECTION_NARROWED` | ✅ | ✅ | `True` | `True` |
| `TRAINING_CLASS`（如"社会科学试验班"） | ✅ | `None` | `True` | `False` |
| `UNCLASSIFIED` | `None` | `None` | `False` | `False` |

> `TRAINING_CLASS` 是"**已分类但专业类未知**"——知道它是工科试验班，但试验班跨多个专业类。
> 它**不参与**"同一专业类"打分档（那会过度奖励），但**参与**"同一门类"档。

## 5. 与 `scoring.major_match_score` 的衔接

| 匹配关系 | 得分 | 层级标签 | 判据 |
|---|---|---|---|
| 与意向**专业名**完全一致 | 1.00 | `EXACT_MAJOR` | 原文或**去方向后的基名**命中 |
| 同一**专业类** | 0.80 | `SAME_DISCIPLINE` | L2 相等 |
| 同一**学科门类** | 0.55 | `SAME_CATEGORY` | L1 相等 |
| **相关门类** | 0.30 | `RELATED_CATEGORY` | `RELATED_CATEGORY_MAP` |
| 不在意向范围 | 0.00 | `NONE` | — |
| **未填意向** | 1.00 | `NO_INTENT` | "不限制" ≠ "全都不匹配" |

三个必须记住的细节：

1. **`major` 行为空也能匹配**：`resolve_major_taxonomy()` 会用专业名现算兜底。
   原实现要求调用方先查出 `Major` 行且其 `category`/`discipline` 非空 —— 这正是缺陷根源。
2. **方向后缀不打断匹配**：意向填 `计算机科学与技术` 时，
   `计算机科学与技术(基础拔尖基地班)` 仍得 1.00（按基名匹配）。
3. **意向里误填方向词会被忽略**：`intended=["中外合作办学"]` 返回 `NO_INTENT`（1.00）而不是
   0.00。方向词是 `filters.py` 的**筛选条件**，不是专业意向；否则会静默把考生所有专业判成不匹配。

每个得分都带 `ScoreBreakdown.major_match_level` 与 `major_category`/`major_discipline`/
`admission_direction`/`direction_kind`，满足"每个分数必须能追溯到具体规则"（DOMAIN_RULES §5）。

## 6. 回填与覆盖度（实测）

### 6.1 两条回填路径

| 路径 | 命令 | 适用 |
|---|---|---|
| 装载时回填 | `scripts/seed.py --reset --source hybrid` | 重新播种（**会清空考生档案/志愿表/对话**） |
| **原地迁移** | `scripts/backfill_major_taxonomy.py --apply` | **已有数据库**，幂等，不碰用户数据 |

原地迁移只填 `category` 与 `discipline` **同时为空**的行，已有的不动，可安全重复执行。

### 6.2 实测覆盖度（浙江 2026 · 18,543 个投档单位）

| 判定来源 | 单位数 | 占比 |
|---|---|---|
| `CATALOG_EXACT` | 17,080 | 92.1% |
| `DISCIPLINE_NAME` | 790 | 4.3% |
| `KEYWORD_RULE` | 404 | 2.2% |
| `TRAINING_CLASS` | 141 | 0.8% |
| `DIRECTION_NARROWED` | 99 | 0.5% |
| `UNCLASSIFIED` | 29 | **0.2%** |
| **门类级覆盖率** | **18,514** | **99.84%** |
| **专业类级覆盖率** | **18,373** | **99.08%** |

剩余 0.2% 是**极少数新专业名**与个别机构名（如"商学院""理工学院"），
**刻意保持为空**——它们是真实的数据缺口，不是待猜的填空题。

### 6.3 对推荐结果的实测影响（A/B，同一考生 630 分）

| 指标 | 回填前 | 回填后 | 变化 |
|---|---|---|---|
| 通过硬过滤候选 | 17,875 | 17,875 | 0 |
| 可评估（有概率） | 15,333 | 15,281 | **−52** |
| `NO_DATA` | 2,542 | 2,594 | **+52** |
| `data_coverage` | 0.8578 | 0.8549 | −0.29pp |
| utility 取值数（全池） | 83 | 83 | 0 |

**这 52 个单位的"减少"是修正，不是退化**：它们原先靠"任意专业"的类比池拿到概率
（如拿 985 院校里**任意专业**类比"社会学"），现在因**同专业类**类比池 <3 个而诚实地返回
`NO_DATA`。代价是 0.29pp 覆盖率，换来的是不再跨专业编造概率。

> ★ **待办（M7）**：可考虑给 Step 0 加"**保持专业类不变、逐级放宽地区/层次**"的类比阶梯，
> 在不跨专业类的前提下把覆盖率补回来。**必须先用回测验证**再改（AGENTS.md §6.9）。

## 7. 规则库不变量（由测试强制）

`scripts/build_major_taxonomy_data.py` 与 `tests/test_major_taxonomy.py` 双重校验：

1. 本科恰好 **12 门类 / 93 专业类**；专科恰好 **19 大类**。
2. 专业类**不得跨门类重名**（否则 `category_of` 有歧义）。
3. `direction_narrowing` 的值必须是**专业类**；
   `direction_category` / `training_class_rules` 的值必须是**门类**。
   > 实测踩过：`"卓越工程师": "工学"` 把**门类**填进了**专业类**字段，
   > 导致该专业的 `category` 变成 `None`。这条不变量就是为了拦住这类错误。
4. `major_exact` 的值、`discipline_keywords` 的键必须是合法专业类（本科 ∪ 专科）。
5. `major_exact_by_level` 的键必须在 `major_exact` 里有对应条目（否则是**死规则**），
   学制键只能是 `BENKE`/`ZHUANKE`，值必须是合法专业类。
6. **JSON 不得出现重复键**（见 §7.1）。
7. 真实语料上的覆盖率**不得回退**（`TestCoverageRegression`，含浙工大全部 50 个专业）。

### 7.1 ★ JSON 重复键：一个会"静默改数据"的坑（2026-09 实测）

JSON 规范**允许**同一对象出现重复键，解析器**取最后一个** —— 于是分批追加条目时，
后写入的值会**静默覆盖**先写入的值，**没有任何报错**。

实测 `major_exact` 里积了 **554 个重复键**，其中 **7 个值冲突**，
导致 4 个专业名被归错类、影响 **110 行**真实数据：

| 专业名 | 曾被归到（错） | 正确 | 依据 |
|---|---|---|---|
| `交通管理` | 公安学类 | **公共管理类** | 本科 120407T；公安技术类里叫 `交通管理工程`(083103TK) |
| `人力资源管理` | 公共管理类 | **工商管理类**（本科） | 本科 120206 属工商管理类；专科 590202 才属公共管理类 |
| `智慧海洋技术` | 海洋科学类 | **海洋工程类** | 与关键词层一致（`智慧海洋`） |
| `社区管理与服务` | 社会学类 | **公共管理类** | 与关键词层一致 |

**三层防护已就位**：

1. `build_major_taxonomy_data.py` 开头有**重复键守卫**，发现重复直接 `exit 1`；
   它是**逐对象**检测（用 `object_pairs_hook`），所以 9 个方向类型各自的
   `label`/`keywords`/`notes` 不会被误报。
   > ⚠️ 早期版本的检测脚本做了**全文扁平扫描**，把嵌套同名键误报成 3 个冲突 ——
   > 这个误报本身也被写成了回归用例（`test_duplicate_detector_is_object_scoped_not_flat`）。
2. `tests/test_major_taxonomy.py::TestNoDuplicateJsonKeys` 直接断言 JSON 无重复键，
   并反向验证"检测器对真重复必须报警"（防止守卫自己失效）。
3. `scripts/dedupe_major_taxonomy.py` 负责消解：**逐条人工判定**冲突值（判定依据写在脚本
   docstring 里），而不是依赖"最后一个生效"这种巧合；同时把键**排序**输出，
   让重复键再也藏不住。

`TestConflictResolutions` 把 7 个判定逐个钉死，防止以后又被改回去。

### 7.2 同名专业的两级分裂：`major_exact_by_level`

有些专业名在**本科与专科属不同专业类**。`major_exact` 只能给一个值，
因此新增按学制分流的覆盖表：

```json
"major_exact_by_level": { "人力资源管理": { "ZHUANKE": "公共管理类" } }
```

语义：`major_exact` 给**默认（本科）**口径；`major_exact_by_level` 在**学制已知且匹配**时覆盖。
学制未知时**不猜**，用默认口径并在 `evidence` 里注明"该名在 ZHUANKE 下有不同归属"。

| 专业名 | 本科 | 专科 | 真实数据 |
|---|---|---|---|
| `人力资源管理` | 工商管理类 | 公共管理类 | 本科 78 单位 / 专科 6 单位 |

## 8. 如何扩充规则库

遇到 `UNCLASSIFIED` 的专业名，按以下顺序处理（**不要跳过第 4 步**）：

1. 在 `major_taxonomy.json` 的 `major_exact` 加**精确名 → 专业类**（最稳，优先）。
2. 若是一类命名模式，加进 `discipline_keywords[专业类]` 的关键词表。
3. 若是大类招生，加进 `training_class_rules`（门类）或 `direction_narrowing`（专业类）；
   若同名专业本科/专科归属不同，加进 `major_exact_by_level`。
4. 跑 `python scripts/build_major_taxonomy_data.py`
   —— **重复键守卫 + 不变量校验会拦住值域错误**。
5. 跑 `pytest backend/tests/test_major_taxonomy.py -q`。
6. 看改动影响面，再决定是否写库：

   ```powershell
   # 只补空值（首次回填；幂等，不碰用户数据）
   python scripts/backfill_major_taxonomy.py
   python scripts/backfill_major_taxonomy.py --apply

   # 规则改动后**重新归类已有行**（会改已有值，先预演看清 diff）
   python scripts/backfill_major_taxonomy.py --reclassify
   python scripts/backfill_major_taxonomy.py --reclassify --apply
   ```

> ★ 两种模式的区别：默认模式只填 `category` 与 `discipline` **同时为空**的行
> （尊重已有口径，不会误改）；`--reclassify` 会重算**所有**行并只更新真正变化的，
> 且预演时打印逐条 `旧 → 新` diff。**改了规则库一定要跑 `--reclassify`**，
> 否则新规则只对新播种的数据生效。

## 9. 已知边界（诚实披露）

- **专科大类展示不完整**：`zhuanke_categories` 的专业类清单为常见项整理，非目录全文。
- **专科与本科共用专业类词汇**是项目约定（§3.1），不是教育部口径。
- **`discipline_keywords` 是启发式**：`分析检验技术` 这类名字可同时归入化工/环境，
  规则取**最长关键词优先**的确定性结果，不保证与某位专家的直觉一致。
  可用 `evidence` 字段审计每条判定。
- **试验班（`TRAINING_CLASS`）只到门类**：141 个单位（0.8%）无法定到专业类，
  因为它们**本身就是跨专业类的大类招生**。这是事实，不是缺陷。
- **未做学科评估等级**：`majors.subject_eval_grade` 仍为空（官方投档表不发布）。
